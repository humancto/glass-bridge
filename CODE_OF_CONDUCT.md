# GlassBridge community code of conduct

GlassBridge is a security and systems research project. Productive participation
requires technical candor, respect for prior art, and care with claims that may
affect real security decisions.

## Our standards

Examples of behavior that strengthens this community include:

- treating contributors with respect regardless of background, identity,
  experience, employer, or point of view;
- criticizing ideas, measurements, and code without attacking people;
- publishing enough context for results and failures to be reproduced;
- crediting prior art and distinguishing implemented behavior, measurements,
  hypotheses, and marketing claims;
- handling security reports privately until coordinated disclosure is
  appropriate; and
- removing private, operational, or proprietary data from public artifacts.

Unacceptable behavior includes harassment, threats, discriminatory language,
deliberate misrepresentation of results, publication of another person's private
information, or disclosure of an unresolved vulnerability in a way that creates
avoidable harm.

## Scope

This code applies to repository discussions, issues, pull requests, reviews,
project events, and other spaces where someone represents GlassBridge.

## Reporting and enforcement

Report conduct concerns privately to the repository maintainer through the
contact method on the maintainer's GitHub profile. Report security
vulnerabilities through GitHub private vulnerability reporting as described in
[SECURITY.md](SECURITY.md).

Maintainers may edit or remove contributions, temporarily limit participation,
or permanently exclude participants when necessary to protect the community.
Reports will be reviewed as privately and promptly as practical. Retaliation
against a good-faith reporter is not acceptable.

## Enforcement principles

Responses should be proportional, consistent, and focused on preventing further
harm. A maintainer involved in a report should recuse themselves when another
qualified maintainer is available. As the project grows, this process should be
replaced by a named multi-maintainer response group with a documented appeal
path.

# Milestone 10: fast binary browser transport

Milestone 10 replaces the browser demo's conservative 512-byte, 4-FPS text
default with a measured fast path while preserving the signed envelope, local
policy, memory quarantine, explicit release, replay, and receipt boundaries from
Milestones 8 and 9.

## What was slow

The milestone 9 sender paid three independent costs:

1. each 556-byte AGF1 frame was base64url-wrapped before QR encoding, growing it
   to roughly 750 characters and raising its QR version;
2. the sender used only 512 useful bytes per frame at 4 FPS; and
3. the animation waited a complete frame interval *after* QR rendering, so render
   time was added to every interval and the displayed FPS control overstated the
   achieved cadence.

For a 144 KiB transport payload, that profile has 288 source symbols and a
72-second loss-free minimum before envelope overhead.

## Implemented profiles

| Profile | QR payload | Symbol | Default | Nominal | 144 KiB payload-only minimum |
|---|---|---:|---:|---:|---:|
| Fast (default) | raw AGF1 byte segment | 1,536 B | 12 FPS | 18 KiB/s | 8.0 s |
| Balanced | raw AGF1 byte segment | 1,024 B | 10 FPS | 10 KiB/s | 14.4 s |
| Legacy | `AGF1B64:` text | 512 B | 4 FPS | 2 KiB/s | 72.0 s |

The actual sender estimate uses the signed envelope size, not the original file
size. A one-way sender cannot know when the phone has completed, so the operator
must continue aiming until the receiver reports **QUARANTINED**.

## Binary QR interoperability

The AGF1 frame format did not change. Fast and Balanced put the existing binary
frame directly into one QR byte segment. The receiver reads ZXing's
`BYTE_SEGMENTS` metadata and passes that exact segment to the bounded AGF1 parser.
It still accepts milestone 9 `AGF1B64:` text, and the sender retains Legacy as an
operational fallback.

At medium QR error correction, a 1,580-byte Fast frame is QR v33 in byte mode.
The same frame as base64 text is QR v39. Binary mode therefore carries three
times the old source symbol while remaining less dense than its text equivalent.

`tests/fixtures/browser-fast-frame-v33.png` is generated by JavaScript's `qrcode`
package. The Rust `browser_binary_interop` test decodes that image with Quirc and
compares the result byte-for-byte with Rust's deterministic AGF1 encoder. This
locks the browser-to-native binary representation without changing AGX or AGF1.

## Render and scan pipeline changes

- The sender schedules against a monotonic deadline. QR render time is subtracted
  from the next delay instead of being added to it.
- The offscreen render canvas is reused rather than allocated for every frame.
- The UI reports the measured render FPS once per second.
- QR modules use an integer pixel scale and the standard four-module quiet zone;
  supported laptop viewports preserve the canvas's intrinsic pixel grid.
- The receiver scans immediately after a successful frame and retries after 16
  ms on a miss.
- Receiver progress painting is limited to roughly 12.5 updates per second while
  every decoded frame still reaches the fountain decoder.
- Service-worker navigations are network-first with an offline fallback, avoiding
  an old-HTML/new-asset race during deployment while static assets remain
  cache-first.

In a production-build browser run at a 1,280 × 720 viewport, the Fast stream
sustained **12.0 rendered FPS** for the observed interval. This validates the
sender scheduler and QR render path only. It does not measure camera goodput.

## Security invariants

The optimization does not bypass or weaken:

- canonical AGX/1 and COSE Ed25519 verification;
- SHA-256 payload integrity;
- paired sender key and boundary checks;
- bounded frame length, source count, symbol size, and transfer size;
- per-frame CRC and mixed-session rejection;
- default-deny local policy;
- memory quarantine and explicit human release;
- replay reservation; or
- receiver-signed release evidence.

Binary QR data remains hostile input. ZXing output enters the same bounded parser
as a decoded Legacy frame.

## Verification

```bash
npm test
npm run generate:browser-fast-fixture
cargo test --workspace --all-targets --all-features --locked
```

The unit suite covers raw-frame reconstruction, Legacy compatibility, QR-version
regression, the 144 KiB profile calculation, and deadline scheduling. The Rust
suite independently decodes the JavaScript-generated v33-M fixture.

## Honest limitations and next measurements

Fast is the default because it is the most useful show-and-tell profile, but it
is not yet a universal device claim. The physical device matrix must record phone
model, OS/browser, laptop/display, distance, angle, brightness, target and
achieved sender FPS, receiver accepted-frame rate, time to quarantine, retries,
and thermal behavior for 1 KiB, 32 KiB, 144 KiB, and 256 KiB files.

The next transport milestone should add receiver-visible scan-rate telemetry and
an optional optical backchannel before calling the system adaptive. Until then,
profile changes are operator-controlled: Fast first, Balanced for focus or frame
loss, and Legacy for older cached receivers or difficult cameras.
